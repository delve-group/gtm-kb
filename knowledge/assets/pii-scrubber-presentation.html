Why PII Scrubbing? // motivation

  • GDPR & AI Act — personal data must never reach external LLM providers
  • Scrub before inference — clean the message before it leaves our infrastructure
  • Graceful degradation — if Ollama is down, pipeline falls back to Regex + NLP only
User Message → 3-Pass Scrubber → Clean Message → External LLM

Pass 2 & 3 // NLP + Bielik LLM

Pass 2: spaCy NER

  • Polish model pl_core_news_sm
  • Person names → <IMIE_NAZWISKO>
  • Locations → <ADRES>
  • Handles declined forms (Markiem, Marka…)
  • Skips already-tokenized text

Pass 3: Bielik LLM 🆕

  • Local bielik-4.5b-instruct via Ollama
  • Receives original + scrubbed text
  • Returns structured JSON verdict
  • Catches indirect identifiers (tracking IDs, login handles…)
  • Temperature 0.0 for determinism
06 / 12

3-Layer Patching Chain // when Bielik says FAIL

L1
Substring Match
Deterministic replacement — find leaked text → replace with token. Most reliable.
L2
Index-Based Fallback
Use start/end indices from Bielik + SequenceMatcher similarity ≥ 0.5 validation.
L3
Nuclear Re-scrub
Bielik rewrites the entire text with proper tokens. Last resort fallback.

After patching → Re-audit (max 1 retry to prevent infinite loops)

07 / 12

Metrics // TP, FN, FP

🟢
True Positive (TP)
Scrubber correctly found and masked real PII. The sensitive data is gone from the output.
🔴
False Negative (FN)
PII leaked through! Data breach risk — the sensitive value remains in the output unchanged.
🟡
False Positive (FP)
Scrubber was too aggressive — masked harmless text (e.g. a price mistaken for PESEL).

Examples // in practice

✅ TP — Correct Scrub
In: "Email: jan.k@example.com"
Out: "Email: <EMAIL>"
→ TP +1 for EMAIL
❌ FN — Data Leak!
In: "Pesel: 99010112342"
Out: "Pesel: 99010112342"
→ FN +1 · Hard Exit (code 1)
⚠️ FP — Over-Scrubbing
In: "Price: 55030101230 zł"
Out: "Price: <PESEL> zł"
→ FP +1 · Price wiped as PESEL

Flexible masking: wrong token type but text removed? Still TP for safety. Tracked via --show-mismatch.

09 / 12

Recall & Precision // formulas

Recall = TP / (TP + FN)
"How much PII did we catch?"
  • Critical PII (EMAIL, PHONE, PESEL, IBAN) requires 1.00
  • Others require ≥ 0.95
Precision = TP / (TP + FP)
"How accurate are our redactions?"
  • Tracked as a proxy metric
  • Does not block CI

Hard Leakage Detectors — secondary regex scan on output → triggers instant fail (exit 1)

Key Takeaways // summary

🛡️ 3-layer defense — Regex → NLP → LLM, each catches what the previous missed
🧠 Context-aware — validators + monetary context prevent false positives
🔧 Auto-patching — 3-layer chain fixes leaks automatically when Bielik detects them
🏠 Local LLM — Bielik runs via Ollama, no data leaves infrastructure
✅ Safety first — flexible masking: wrong token ≠ failure, only true leaks fail
🤖 Automated evals — synthetic generation + judge ensure continuous quality
